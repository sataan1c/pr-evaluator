# AI-оценщик вклада по PR

**Открыть дашборд онлайн, без установки:** https://sataan1c.github.io/pr-evaluator/

Это статичная страница со всеми данными внутри (`docs/index.html`); её же можно скачать и открыть двойным кликом без интернета.

Система читает принятые pull request'ы репозитория, оценивает каждый моделью по четырём критериям (сложность, качество, риск, ясность) с объяснением и ссылками на строки кода, считает для каждого разработчика множитель относительно нормы его уровня и проверяет, можно ли этим оценкам верить. Результат показывает дашборд на трёх языках: азербайджанском, русском и английском.

Пример построен на репозитории [pydantic/pydantic](https://github.com/pydantic/pydantic): 150 последних принятых PR.

## Запуск

Нужен Python 3.9 или новее (проверено на 3.13).

```
pip install -r requirements.txt
python run_all.py
```

Команда досчитывает то, чего не хватает, и открывает дашборд в браузере. Токен GitHub, ключ модели и интернет ей нужны, только если не хватает выгрузки или оценок. Всё остальное считается на готовых файлах за секунды.

## Как получить оценки модели без денег на API: Claude Code CLI

Если у кого-то в команде есть подписка Claude Pro или Max, ключ API и баланс не нужны.
`score.py` вызывает Claude Code CLI (`claude -p`), а запросы идут в счёт лимитов подписки.

1. Установите Claude Code ([инструкция](https://docs.claude.com/en/docs/claude-code/overview)),
   запустите в терминале `claude` и войдите в аккаунт с подпиской. Это делается один раз.
2. Оцените пять PR и прочитайте результат глазами:

```
python score.py --provider claude-cli --limit 5 --runs 1
```

   Или просто `python score.py` и ответ `5` на первый вопрос: настройка сохранится в `.env`
   (`SCORER_PROVIDER=claude-cli`), ключ не спрашивается.
3. Полный прогон, бережно к лимитам подписки:

```
python run_all.py --runs 1 --no-style
```

Что важно знать:

- Модель по умолчанию `claude-haiku-5-5`: быстрее и меньше тратит лимиты. Качественнее, но дороже по лимитам:
  `--model claude-sonnet-5-5`. Одна модель на весь прогон.
- Один запрос — примерно 30–40 тысяч входных токенов (сам PR плюс служебная часть Claude Code).
  150 PR с одним прогоном — 150 запросов. Если лимит подписки закончится, скрипт остановится с понятным
  сообщением; готовое останется в `cache/`, и следующий запуск после сброса лимита доделает только недостающее.
- Одновременно оцениваются 2 PR (`--workers`). Claude запускается с выключенными инструментами
  (`--tools ""`) в пустой временной папке: он только читает текст PR и ничего не выполняет.
- В `run_stats.json` поле `api_list_price_usd` показывает, сколько те же запросы стоили бы через API.
  По подписке эти деньги не списываются.
- Проверено на двух настоящих PR из `data/prs.json`.

## Как получить оценки модели через API

1. Возьмите ключ любого сервиса с OpenAI-совместимым API. Бесплатный вариант без карты: [Google AI Studio](https://aistudio.google.com/apikey).
2. Оцените пять PR и прочитайте результат глазами:

```
python score.py --limit 5
```

При первом запуске скрипт спросит сервис, ключ и название модели, проверит связь и сохранит ответы в `.env`. Этот файл перечислен в `.gitignore` и в репозиторий не попадает.

3. Запустите полный прогон:

```
python run_all.py
```

Он оценит остальные PR (уже оценённые берутся из кэша в `cache/`), посчитает множители, тест стиля, валидацию и откроет дашборд.

`--limit` и `--only` не стирают оценки, которые уже лежат в `scores.json`: остальные PR остаются в файле, если они получены тем же промптом и той же моделью. Если промпт или модель другие, файл заменяется, и скрипт об этом предупреждает.

На бесплатном тарифе с лимитом запросов добавьте в `.env` строку `SCORER_RPM=10` (или ниже вашего лимита). Быстрый и дешёвый вариант: `python run_all.py --runs 1 --no-style`. Один проход по 150 PR — это 150 запросов и примерно 600 тысяч входных токенов; полный прогон с тремя проходами и тестом стиля — около 540 запросов.

Все PR оценивайте одной моделью: баллы разных моделей нельзя сравнивать между собой.

## Посмотреть готовый дашборд без ключа

```
python app.py demo
```

Команда прогоняет весь путь на выдуманном репозитории: вместо GitHub и нейросети работают две локальные заглушки. Результат ложится в `demo_out/`, дашборд напоминает жёлтой полосой, что баллы поставила заглушка. Цифры оттуда ничего не доказывают и на слайд не идут.

## Команды

| Команда | Что делает |
| --- | --- |
| `python run_all.py` | Досчитать недостающее и открыть дашборд |
| `python run_all.py --no-app` | Только посчитать |
| `python run_all.py --rescore` | Оценить заново после правки рубрики |
| `python run_all.py --force` | Заново выгрузить PR из GitHub и оценить всё, чего нет в кэше |
| `python run_all.py --update --no-app` | Для cron: свежий список PR из GitHub, оценить только новые, пересчитать метрики |
| `python classify.py` | Определить тип изменения каждого PR (один короткий запрос на PR, готовое берётся из кэша) |
| `python app.py` | Только дашборд на данных из `data/` |
| `python app.py serve --dir ПАПКА` | Дашборд на данных из другой папки |
| `python app.py check` | Проверка формата и согласованности файлов |
| `python app.py test` | Тесты проекта |

Каждый шаг запускается и отдельно, из корня проекта: `python outcomes.py`, `python metrics.py`, `python validate.py` и так далее. Файлы они сами берут из `data/` и пишут туда же. Параметры описаны в начале каждого скрипта и в `--help`.

Репозиторий и число PR задаются в начале `run_all.py` (`REPO`, `LIMIT`).

## Как устроен конвейер

| Шаг | Скрипт | Читает | Пишет | Нужно |
| --- | --- | --- | --- | --- |
| 1 | `fetch_prs.py` | GitHub API | `prs.json`, `all_prs.json`, `author_history.json` | сеть, токен GitHub |
| 2 | `check_data.py --only-prs` | `prs.json` | — | — |
| 3 | `score.py` | `prs.json`, `rubric.md` | `scores.json`, `run_stats.json` | ключ модели |
| 3б | `classify.py` | `prs.json` | `change_types.json` | та же модель, что у `score.py` |
| 4 | `outcomes.py` | `prs.json`, `all_prs.json` | `outcomes.json` | — |
| 5 | `metrics.py` | `prs.json`, `scores.json`, `author_history.json`, `config/levels.json` | `metrics.json` | — |
| 6 | `style_test.py` и `score.py` | `prs.json`, `scores.json` | `prs_style.json`, `scores_style.json`, `style_report.json` | ключ модели |
| 7 | `validate.py`, `chart.py` | всё перечисленное и `human_scores.csv` | `validation.json`, `validation.md`, `risk_chart.png` | — |
| 8 | `check_data.py` | все файлы | — | — |

Все файлы данных лежат в `data/`.

Что делает оценку проверяемой:

- автор PR от модели скрыт, в том числе его логин в тексте diff;
- каждый PR оценивается три раза, в файл идёт медиана, расхождения помечаются флагом;
- ссылки модели на строки кода сверяются с настоящим diff, выдуманные убираются;
- комментарии и ревью, написанные после мержа, выгрузка отбрасывает: они выдали бы исход (про уже выгруженные данные см. «Ограничения»).

## Тип изменения

Кроме четырёх баллов, модель относит каждый PR к одному типу по его главной цели:
новая функция, исправление, производительность, рефакторинг, документация, тесты, сборка и CI.
Это делает `classify.py` отдельным коротким запросом (заголовок, описание, список файлов и начало diff, автор скрыт),
поэтому оценки в `scores.json` и сравнение с человеком от него не зависят.

Тип — справка, а не оценка: в множитель он не входит. Он показывает, из какой работы сложились баллы:
у одного разработчика в основном исправления, у другого документация. В дашборде тип виден на странице PR
(с причиной), в списке PR (метка под заголовком и фильтр), в профиле разработчика (разбивка «Чем занимается») и в таблице команды.
REST-отчёты отдают его в поле `change_types`.

Граница между «новой функцией» и «исправлением» бывает спорной: PR вида «Allow X» модель относит к исправлению,
если описание говорит, что раньше X ошибочно не работал. С человеком тип не сверялся.

## Работа по расписанию (cron)

Так система работает как сервис из схемы POC: сама забирает новые вмерженные PR и оценивает каждый один раз.

```
*/10 * * * * cd /path/to/pr-evaluator && python3 run_all.py --update --no-app >> cron.log 2>&1
```

На Windows то же через Планировщик заданий:
`schtasks /Create /SC MINUTE /MO 10 /TN "PR Evaluator" /TR "python C:\path\to\pr-evaluator\run_all.py --update --no-app"`.

`--update` заново берёт из GitHub только список PR (сами PR лежат в кэше `raw/`), новые PR оценивает,
а уже оценённые берёт из `cache/`, затем пересчитывает исходы, множители и проверку метода.
Роль «базы» из схемы играют файлы в `data/` и кэш: каждый PR оценивается ровно один раз.

## REST API для отчётов

Пока работает `python app.py`, тот же сервер отвечает на запросы отчётов:

```
GET http://127.0.0.1:8765/api/reports/employees/{employeeId}
GET http://127.0.0.1:8765/api/reports/team
```

`employeeId` — логин автора на GitHub. Период по дате мержа: `?since=2026-08-01&until=2026-09-30`.
Отчёт по сотруднику: число PR, медианы по четырём критериям, медианы команды и разница с ними,
уровень, множитель, флаги, сравнение с людьми того же уровня, список PR со ссылками.
Множитель считается `metrics.py` за весь период; при фильтре по датам это помечено полем `multiplier_period: "all"`.

## Дашборд

- **Команда.** Таблица разработчиков с линейкой множителя.
- **Разработчик.** Множитель и из чего он сложился, чем занимается (разбивка по типам изменений), профиль баллов, его PR.
- **Разбор PR.** Тип изменения с причиной, четыре балла, причина каждого и строки кода, на которые сослалась модель. Поле «Контекст от автора» сохраняется в `data/notes.json`.
- **Pull requests.** Поиск, фильтры (в том числе по типу изменения), сортировка.
- **Проверка метода.** График риска с интервалами, сравнение с человеком, тест стиля, стабильность.

Язык интерфейса переключается кнопками AZ, RU, EN в шапке. Суть PR и причины баллов пишет модель, и дашборд их не переводит; их язык задаётся при оценке: `python app.py run --lang az` (или `ru`, `en`). Подробности в `dashboard/README.md`.

## Ручная оценка

В `data/human_scores_template.csv` лежит бланк на 20 PR со ссылками. Заполните столбцы баллами от 1 до 5 по `rubric.md`, не глядя в `scores.json`, сохраните как `data/human_scores.csv` и запустите `python run_all.py`. Это можно делать уже сейчас, до оценок модели. Бланк другого размера: `python validate.py --human-template 30`.

## Что проверяет валидация

1. **Риск против исходов.** Доля откаченных и срочно исправленных PR по группам балла риска, с интервалами. Рядом тот же расчёт для простого размера PR: видно, знает ли модель что-то сверх «большой PR опасен».
2. **Человек против модели.** Доля совпадений в пределах одного балла.
3. **Тест стиля.** То же изменение с небрежным описанием: ясность должна упасть, остальные баллы нет.
4. **Стабильность.** Сколько PR получили разные баллы в разных прогонах, сколько ссылок на код пришлось убрать.

Вывод «связь есть» отчёт делает, только если нижняя граница интервала выше случайного угадывания. Если проблемных PR меньше пяти, вывода нет вообще.

## Тесты

```
python app.py test
```

199 тестов, около полутора минут. Сети и ключей не требуют: выгрузка и оценка проверяются на локальных заглушках из `devtools/`, Claude Code CLI — на заглушке в `tests/test_claude_cli.py`. Настройки из `.env` в корне проекта тесты не читают (скрипты в них запускаются с `SCORER_IGNORE_PROJECT_ENV=1`), поэтому `SCORER_PROVIDER=claude-cli` в `.env` не включит в тестах настоящую модель. На Windows тесты с заглушкой Claude Code CLI пропускаются.

## Ограничения

- **Каждый PR оценён один раз.** Стабильность (три прогона и медиана) на этих данных не проверялась.
- **Через API код с настоящей моделью не запускался.** Все 150 оценок получены через Claude Code CLI; путь через API проверен только на локальной заглушке.
- **В настоящих данных мало проблемных PR.** Окно наблюдения в 14 дней прошло у 103 PR из 150, и только у двух из них было исправление вслед; откатов среди них нет. С таким числом отчёт честно скажет «данных мало». Чтобы проверка риска что-то показала, нужна выборка больше и старше: `python run_all.py --force --limit 400` (по умолчанию берутся PR не моложе 30 дней).
- **Данные выгружены предыдущей версией `fetch_prs.py`.** Она не отбрасывала ревью, написанные после мержа, а текущая отбрасывает. Перевыгрузка (`--force`) это исправит. Текущая версия `fetch_prs.py` проверена на заглушке GitHub, с настоящим API она ещё не запускалась; предыдущая версия есть в истории git.
- **Азербайджанский перевод** интерфейса стоит дать прочитать носителю языка. Все тексты лежат в `dashboard/i18n.js`.
- Откаты прямым коммитом в main и исправления без ссылки на исходный PR не видны.
- Уровни разработчиков в открытом репозитории заданы допущением по числу прошлых PR. В компании их задают в `level_overrides` в `config/levels.json`.
- Нормы уровней в конфиге стартовые. Когда на уровне наберётся пять разработчиков с тремя и более PR, норма берётся из данных.
- Открытый репозиторий мог попасть в обучающие данные модели.

`token.txt`, `.env` и ключи в репозиторий не попадают: они перечислены в `.gitignore`.
